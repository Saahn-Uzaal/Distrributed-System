## F05 — Test tamper chữ ký phải thật sự đổi byte (làm trước, theo brief)

**Vấn đề:** test "tampered token" cũ không chứng minh được rằng byte chữ ký thực sự bị thay đổi trước khi gọi endpoint.

**Thay đổi:**
- `identity-service/src/test/java/com/ridehailing/identity/AuthFlowIntegrationTest.java`: test tamper giờ (1) decode phần signature của JWT, (2) clone mảng byte gốc để so sánh, (3) lật bit 0 của byte đầu tiên của chữ ký, (4) assert mảng đã đổi khác mảng gốc **trước** khi encode base64url (không padding) và gọi `GET /api/auth/me`, (5) expect 401.

**Lệnh + kết quả:**
- Chạy riêng test này trong lượt đầu: **thất bại một lần** — lỗi ở chính test (so sánh mảng đã biến đổi với bản thân nó, không phải bản clone gốc). Sửa logic so sánh rồi chạy lại → pass.
- `./mvnw -B clean verify` cuối đợt: test tamper nằm trong 12 tests của identity-service, **Failures: 0**.

**Giới hạn:** chỉ chứng minh hành vi reject token chữ ký sai; không kiểm tra thuật toán RSA (đúng scope F05).

## F01 — JWT temporal claims và claim handling an toàn

**Vấn đề:** `JwtService.authenticate` không validate `exp`/`nbf`; đọc claims thiếu/sai kiểu có thể ném `ClassCastException` → 500 thay vì 401.

**Thay đổi:**
- `identity-service/src/main/java/com/ridehailing/identity/service/JwtService.java`:
  - Validate `exp`: bắt buộc, phải là số, chưa hết hạn (so với giờ hiện tại).
  - Validate `nbf` nếu có: đã hiệu lực.
  - **Chốt policy clock skew = 0s** (không tolerance) — ghi trong javadoc của class; không cần inject Clock vì regression tests tự ký token thật với exp/nbf quá khứ/tương lai cố định.
  - Claim handling an toàn: `sub`, `role`, `email` phải là String; `aud` phải là mảng — thiếu/sai kiểu → 401, không còn 500.
  - `loadPrivateKey()`/`loadPublicKey()` đổi sang **public** để T07 tái sử dụng (private key không rời identity-service).

**Regression tests (thêm trong `AuthFlowIntegrationTest`, ký token thật bằng private key RSA sinh trong test):**
- Token hết hạn (`exp` quá khứ) → 401.
- Token chưa hiệu lực (`nbf` tương lai) → 401.
- Token thiếu `aud` / `aud` sai kiểu (string thay vì mảng) → 401, không 500.

**Lệnh + kết quả:** `./mvnw -B clean verify` → identity-service **Tests run: 12, Failures: 0** (6 test cũ + 6 regression mới F01/F03/F04/F05).

## F02 — PaymentSucceeded/PaymentFailed phải route tới Trip trên broker thật

**Vấn đề:** topology chỉ bind `matching.#` → `trip.inbox`; event payment không có binding, trip-service sẽ không nhận được kết quả thanh toán.

**Thay đổi:**
- `infra/rabbitmq/declare_topology.es`: thêm binding `ride.events` → `trip.inbox` với routing key **`payment.#`** (một wildcard phủ cả `payment.succeeded` + `payment.failed`) + comment giải thích.
- `infra/rabbitmq/declare-topology.sh`: cập nhật comment bảng topology.
- `docs/events.md`, `README.md`: cập nhật bảng topology cho khớp broker thật.

**Lệnh + kết quả (broker thật, Docker Desktop đã bật):**
1. `bash infra/rabbitmq/declare-topology.sh` → `T04: topology declared over AMQP (host=rabbitmq).` — idempotent, không xóa queue/volume.
2. Management API `GET /api/queues/%2F/trip.inbox/bindings` → xác nhận bindings `matching.#` + **`payment.#`** (+ DLQ rk=`trip.inbox`).
3. Publish 3 event qua management API (`POST /api/exchanges/%2F/ride.events/publish`, payload base64, `payload_encoding:"base64"`, `delivery_mode:2`): `payment.succeeded`, `payment.failed`, `matching.proposed` → cả 3 trả `{"routed":true}`.
4. Consume từ `trip.inbox` (`POST /api/queues/%2F/trip.inbox/get`, `ackmode:"ack_requeue_false"`) → thấy đúng 3 routing key, payload nguyên vẹn.
5. Dọn message thử: queue về **0**.

**Ghi chú kỹ thuật (đã kiểm chứng trên bản API này):** publish bắt buộc có key `payload_encoding` và chỉ nhận `"base64"` (`auto`/`utf8` bị reject); GET messages cần `encoding:"base64"`; đường dẫn queue phải có vhost segment `%2F`.

## F03 — Đăng ký email trùng đồng thời không được 500 / không tạo user trùng

**Vấn đề:** race hai request register cùng email → `DataIntegrityViolationException` → 500, và/hoặc nguy cơ user trùng.

**Thay đổi:**
- `identity-service/src/main/java/com/ridehailing/identity/exception/GlobalExceptionHandler.java`: handler `DataIntegrityViolationException` **phân biệt** vi phạm unique key: message chứa tên constraint Postgres `users_email_key` → 409 `EMAIL_TAKEN`; mọi `DataIntegrityViolationException` khác giữ 500 (không blanket-map, theo brief).
- Không dùng lock RAM — unique constraint DB là cơ chế bảo đảm cuối cùng.

**Regression test:** register đồng thời 2 request cùng email bằng CountDownLatch barrier → cả hai nhận HTTP response hợp lệ (một 201, một 409 `EMAIL_TAKEN`), không 500; DB chỉ có **1** user cho email đó (assert qua repository).

**Lệnh + kết quả:** nằm trong `./mvnw -B clean verify` → identity-service Tests run: 12, Failures: 0.

## F04 — Validation role/password/fullName đúng contract, không 500 do đầu vào

**Vấn đề:** password >72 byte UTF-8 làm BCrypt ném exception → 500; `role` null không bị chặn sớm; fullName chưa validate sau trim.

**Thay đổi:**
- `identity-service/src/main/java/com/ridehailing/identity/service/UserService.java`: enforce **≤ 72 byte UTF-8** cho password — register → 400 `INVALID_INPUT`; login → kiểm tra **trước** BCrypt, trả 401 `INVALID_CREDENTIALS` cùng message (không lộ email có tồn tại). fullName validate 2–100 ký tự **sau trim**.
- `identity-service/src/main/java/com/ridehailing/identity/web/dto/RegisterRequest.java`: `role` thêm `@NotNull`. DTO giữ `@Size(max=100)` theo char cho fullName (contract ghi rõ byte-limit chỉ áp dụng password).
- Mới: `identity-service/src/main/java/com/ridehailing/identity/exception/InvalidInputException.java`.
- `docs/api-contracts.md` §3.1: cập nhật văn bản validation (72-byte, trim fullName, role bắt buộc).

**Regression tests:**
- Password đúng 72 byte UTF-8 → register 201; password 73 byte → 400 `INVALID_INPUT` (không 500).
- Login với password >72 byte cho email tồn tại và không tồn tại → cùng 401 `INVALID_CREDENTIALS`, message giống nhau.
- Register role null → 400; fullName có khoảng trắng đầu/cuối được trim rồi validate.

**Lệnh + kết quả:** nằm trong `./mvnw -B clean verify` → identity-service Tests run: 12, Failures: 0.

## F06 — Thống nhất contract replay / NO_DRIVER / phase matching lại (chỉ tài liệu)

**Vấn đề (3 mâu thuẫn giữa docs):**
1. Replay reserve có thể hiểu trả status khác với lần đầu → chốt **trả nguyên response đã lưu, kể cả HTTP 201**.
2. Nhánh terminal `NO_DRIVER` bỏ quên reservation hoặc reserve chưa rõ kết quả khi timeout/late-reserve.
3. Bảng phase ghi Saga `RESERVING_DRIVER` trong lúc phát `TripRequested` cho attempt mới — không khớp trạng thái "đang đợi proposal".

**Thay đổi:**
- `docs/api-contracts.md`: §4.2 replay reserve trả status gốc 201 (quy định duy nhất); NO_DRIVER chỉ terminal **sau khi release/reconcile xong**; reconcile timeout dùng reservationId ổn định; late-reserve nhận `TOMBSTONED_RESERVATION`.
- `docs/state-machines.md`: phase matching lại = **`WAITING_MATCH`** cho đến khi có candidate đúng attempt (DriverProposed); chỉ chuyển `RESERVING_DRIVER` sau đó. Ghi rõ nhánh "dùng lại candidate cũ" là không được phép ngầm — stale-event guard giữ nguyên.

**Nghiệm thu:** đối chiếu transition/contract giữa 3 docs (không code handler Saga/reservation — các task T10/T11/T15/T16/T19/T21 chưa tồn tại, đúng scope brief).
