## Mục tiêu

Chứng minh trên hệ thống thật (Docker Compose, broker/DB thật) rằng:
- **R01**: dừng matching-service giữa chừng không mất message — outbox/inbox giữ `TripRequested` trong queue; start lại trong deadline thì trip tiếp tục bình thường; quá deadline thì trip kết thúc hợp lệ NO_DRIVER và event stale bị skip có audit log (không reserve nhầm).
- **R02**: crash payment-service đúng cửa sổ "sau DB commit, trước ACK" → broker redelivery message cũ → consumer dedup theo eventId → KHÔNG tạo payment trùng; trip vẫn SUCCEEDED với đúng 1 payments row.

## Chốt thiết kế (chưa được user phê duyệt — người thực hiện tự quyết)

- **R01 stop/start matching bằng `docker stop`/`docker start ridehailing-matching-service`** ở tầng container — spec §13 yêu cầu "fault injection chỉ bật bằng profile/env test, không đưa endpoint kill/crash ra public", nên không thêm API kill; dừng container là cách kiểm soát được cửa sổ lỗi.
- **Baseline depth=0**: `rabbitmqctl purge_queue matching.inbox` trước mỗi phase để depth đo được đúng message của trip vừa tạo (không lẫn message run cũ).
- **R02 failpoint xác định** theo spec §13 ("dùng failpoint xác định sau commit trước ACK, không dựa vào kill ngẫu nhiên"): hook test-only `PaymentInboxListener.sleepFailpoint()` đọc env `APP_INBOX_FAILPOINT_DELAY_MS` (property `app.inbox.failpoint-delay-ms`) và sleep 8000 ms **giữa DB commit và ACK**. Bật bằng **compose override file tạm sinh lúc chạy** (`mktemp -d`, truyền làm `-f` thứ hai, đường dẫn Windows qua `cygpath -w`) — cố tình KHÔNG đưa vào `deploy/compose.yaml` tracked (env chuỗi rỗng sẽ crash Spring startup). Sau run, payment-service restart sạch không override.
- **Fresh heartbeat trước create_trip** (r02 và s02): reserve CAS của driver-service yêu cầu `last_seen_at` tươi hơn 15 s (`driver.heartbeat-stale-after-ms=15000`, SQL `casReserveDriver`) — script gửi heartbeat mới + re-affirm AVAILABLE **ngay trước** `create_trip`.
- **Accept theo contract §3.3**: đọc offer qua `GET /api/drivers/me/offer` → extract tripId + attempt (helper `json_number`) → POST accept với body `{"attempt":N}`; loop ≤5 lần tới state=ACCEPTED (saga confirm pattern, như `scripts/smoke-trip.sh`). start/complete trả **200** (không 202).
- **Cancel chấp nhận cả 200|202**: contract §3.3 — cancel từ SEARCHING → 200 CANCELLED ngay; từ DRIVER_OFFERED → 202 CANCELLING rồi chờ terminal.
- **DB assertions read-only qua tài khoản psql của chính service** (`docker exec ... psql -U payment_svc -d payment_db`…) — không cross-service app access (tuân L02).

### Lỗi phát hiện và sửa trong lúc kiểm chứng (lỗi script test, không phải lỗi product)

- **Root cause #1 (R02)**: reserve CAS yêu cầu heartbeat tươi < 15 s. Script cũ gửi heartbeat ở lúc reset rồi chờ ~14–15 s cho payment-service recreate + readiness → d1 stale đúng lúc reserve → `DRIVER_NOT_AVAILABLE`; các lần sau candidates=0 (F02 freshness). Sửa: fresh `heartbeat_d1` + re-affirm AVAILABLE ngay trước `create_trip`.
- **Root cause #2 (R02)**: accept yêu cầu JSON body `{"attempt":N}` từ offer endpoint; start/complete trả 200 chứ không 202. Viết lại đoạn accept theo §3.3 + pattern smoke-trip.sh.
- **Lỗi leftover code**: block accept/start/complete cũ (chờ 202) còn sót sau thay thế awk một phần — chạy sau block mới và fail với thông báo gây hiểu nhầm "accept … HTTP 200". Xóa dòng 282–291 của `scripts/recovery-r02.sh`.
- **Cancel status**: script chỉ chấp nhận 202 → sửa nhận cả `case "$status" in 200|202)` theo contract §3.3 (áp dụng chung r01/r02/s01/s02).
