## Mục tiêu

Payment consumer thật trong payment-service:

- **Migrations** — `inbox_events` (dedup unique `(consumer_name, event_id)`) + `payments` (unique `(trip_id, attempt)`, status `SUCCEEDED`/`FAILED`, `failure_code` nullable) + `outbox` producer payment-service (`event_type CHECK IN ('PaymentSucceeded','PaymentFailed')`).
- **Inbox** — consume `TripCompleted` (rk `trip.completed`) qua queue `payment.inbox`: validate envelope/payload, dedup, ACK sau commit, retry bounded 3 lần (backoff env), hết lượt → DLQ; malformed/unsupported → republish chủ động sang `payment.dlq` kèm `x-dlq-reason`.
- **Nghiệp vụ** — thu tiền giả lập theo cấu hình dev (`PAYMENT_SIMULATE_FAIL_RATE`, default 0): success → payments `SUCCEEDED` + outbox `PaymentSucceeded`; decline → payments `FAILED` + `failure_code=SIMULATED_DECLINE` + outbox `PaymentFailed`.
- **Outbox** — worker publish persistent + mandatory + confirms, `SENT` sau confirm; returned/lỗi → PENDING + `last_error` (mẫu T13).

Acceptance spec §20.5: "Duplicate TripCompleted không thu trùng; success/failure đều có event đúng; amount/currency validation; transaction rollback an toàn."

## Chốt thiết kế

- **Payments ghi status cuối nguyên tử:** row `payments` commit với status `SUCCEEDED`/`FAILED` (kết quả giả lập quyết định trong transaction) + outbox PENDING + inbox dedup record trong MỘT transaction — không có trạng thái PENDING trung gian trên `payments`; `trips.payment_status` giữ `'PENDING'` cho tới khi trip-service nhận PaymentSucceeded/PaymentFailed ở T24. Ghi chú "Chốt T23" trong V3 SQL + javadoc handler + state-machines.md §5.
- **Duplicate business-intent guard (spec §9):** trước ghi, SELECT `payments` theo `(tripId, attempt)` → đã có row thì log + bỏ qua, ACK — không phát event mới. Race song song giữa hai event khác eventId cùng trip/attempt được unique index `uq_payments_trip_attempt` trọng tài: bên thua rollback → retry/redelivery thấy row đã commit → skip (defense-in-depth).
- **Validator chặt payload:** `payload.tripId` phải bằng `envelope.aggregateId` (không thì `malformed_envelope`); currency chỉ chấp nhận đúng `"VND"`; `amountVnd` phải là số nguyên >0 vừa trong long.
- **Cột traceability thêm trên `payments`:** `event_id`, `correlation_id` ngoài schema tối thiểu của spec — nhất quán với pattern `matching_jobs` (truy vết event gốc tạo row).
- **Payment không đọc Trip DB:** `aggregateVersion = 0` và bỏ field này khỏi envelope (§2 optional), như matching T15; `causationId` = eventId của TripCompleted (§5); `correlationId` giữ nguyên từ envelope.
- **Fault injection bọc handler thật** (không probe) — payment không có probe nghiệp vụ, wrapper `@Primary` ném lỗi theo lần attempt rồi delegate về handler thật.

## Kiểm tra (acceptance spec §20.5)

| Acceptance | Bằng chứng |
|---|---|
| Duplicate TripCompleted không thu trùng | `duplicateTripCompletedDoesNotChargeTwice`: publish 2 lần cùng trip/attempt (eventId khác nhau) → đúng **1** row payments, **1** row outbox, 2 row inbox_events; không có event payment thứ hai trên trip.inbox |
| Success/failure đều có event đúng | `tripCompletedProducesPaymentSucceeded`: payments SUCCEEDED + PaymentSucceeded `{tripId, paymentId, attempt, amountVnd}` (§3.5), causation = eventId TripCompleted, correlation giữ nguyên, message persistent trên trip.inbox; `simulatedDeclineEmitsPaymentFailed` (fail-rate=1): payments FAILED + `failure_code=SIMULATED_DECLINE` + PaymentFailed `{tripId, paymentId, attempt, reason}` (§3.6) |
| Amount/currency validation | `malformedAmountOrCurrencyGoesToDlqWithReason`: amount âm / currency sai → republish DLQ kèm `x-dlq-reason=malformed_envelope`, **không** có `x-death`, ACK gốc, không payments/outbox; `unsupportedEventTypeGoesToDlqWithReason`: eventType lạ → `unsupported_event_type` |
| Transaction rollback an toàn | `transientFailureRetriesThenSucceeds`: 2 lỗi transient rồi thành công attempt 3 (ATTEMPTS==3) → đúng **1** row payments + 1 row outbox — rollback không để lại state dở dang; `retryExhaustedGoesToDlqWithoutReasonHeader`: hết retry → DLQ chỉ mang `x-death`, không có payments/outbox/inbox row |

- Simulator là cấu hình dev (`PAYMENT_SIMULATE_FAIL_RATE`, default 0) — không có PSP thật; tỷ lệ fail quyết định kết quả trong transaction.
